# 01-原始需求：数据资产功能模块

## 1. 需求界定 (Triage)
- **反馈类别**：`Requirement (新需求实现)`
- **来源**：用户提供需求规格说明书 (`docs/数据资产功能模块.md`)
- **关联体系**：OpenMetadata 1.7.5 现有框架的扩展模块

## 2. 原始输入摘要
本文档定义了基于OpenMetadata现有框架新增“数据资产”功能模块的详细需求。旨在通过构建资产分类、目录、类型及属性体系，实现对数据资产的规范化管理与展示。主要涉及后端5大实体模型的建设以及前端5个核心导航模块及详情页的交互建设，并且需要无缝接入原有的点赞、历史信息流等公共功能。

## 3. 八何分析法 (5W3H) 深度梳理

### 3.1 Who (谁使用？受众是谁？)
- **数据管理员/数据管家**：负责资产分类、目录结构的搭建，资产类型和自定义属性的规范定义。
- **业务用户/数据分析师**：负责在相应的目录和类型下登记、查找、阅览具体的数据资产。
- **特定授权角色**：在资产属性中被配置为“填写人员”的特定角色，拥有针对性修改权限。

### 3.2 What (做什么？核心价值与产出？)
- **后端建设**：新增五个核心实体（资产分类 `AssetCategory`、资产目录 `AssetCatalog`、资产类型 `AssetType`、资产属性 `AssetAttribute`、数据资产 `DataAsset`）。实现对应的树形层级关联、动态属性绑定、批量导入导出以及级联删除防呆逻辑。融入OM自带的点赞、评论和版本流功能。
- **前端建设**：在侧边栏新增“数据资产”一级菜单及5个二级菜单（概览、资产目录、资产类型、资产属性、数据资产）。全面参考现有 Glossary（术语）、Classification（分类）页面的布局规范。

### 3.3 Why (为什么做？解决什么痛点？)
- OM 原生框架中的“术语库”或“标签”无法完全满足企业内部对“数据资产”多维度、立体化的动态编排与展示需求。通过引入这套独立体系，实现数据资产的规范化、结构化和动态化管理。

### 3.4 Where (在哪里应用？生效范围？)
- **前端页面**：Web 端主页左侧侧边栏增加全新模块。
- **后端架构**：在当前 OM 的后端业务代码中统一下挂于 `asset` 包目录，并在 Elasticsearch 中新增索引用于全局检索。

### 3.5 When (何时使用？触发时机？)
- 当企业需要梳理数据版图、注册新生资产，或数据消费者需要检索和理解特定数据资产上下文时，全天候在 OM 平台上使用。

### 3.6 How (如何实现？核心业务流转？)
1. 管理员首先配置全局 **资产分类** （根）。
2. 在分类下构建树形的 **资产目录**。
3. 定义全局复用的 **资产属性** （区分基本/技术/业务等维度，约定数据类型及填写权限）。
4. 将特定的资产属性打包组合为 **资产类型**。
5. 最终创建具体的 **数据资产**：将其挂载到特定目录下，选定类型，并动态渲染及填写对应的属性表单。
6. 公用功能如 ES 搜索、导入导出、点赞评论贯穿始终。

### 3.7 How Much (做到什么程度？规模及约束？)
- **页面体量**：5个列表页 + 3个详情页。
- **接口功能**：所有实体均需支持增删改查。除基本 CRUD 外，需支持 CSV 批量导入导出、ES 高级搜索条件（AND/OR）。
- **语言约束**：强制要求支持中/英文国际化双语。
- **特殊约束**：
  - 新增实体均**无需**支持逻辑删除（即物理删除）。
  - 删除目录时如果存在挂载的资产，**强拦截并禁止删除**。
  - 删除需输入 `DELETE` 进行二度确认。

### 3.8 How Feel (用户的期望体验？)
- **风格一致性**：新页面必须让用户感觉原生，布局、交互、控件样式（如Tab页、折叠树、按钮组）必须 1:1 参照现有的“探索(Explore)”、“术语库(Glossary)”、“分类(Classification)” 页面结构，降低学习成本。
