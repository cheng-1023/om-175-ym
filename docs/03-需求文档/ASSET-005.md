## 2. 需求说明

### 2.1 现状
新建置的五套庞大实体体系若未受一套统一的公网接入底层基因收容，将无法自然融入开放组件生态中，造成“孤岛现象”，且存在架构散布污染的问题需要钳制。

### 2.2 目标
为数据资产功能模块统一划定系统目录准则、国际化边界语言域字典界限，并接驳 OM 最为基础通用的数管平台公建共用组件簇。

### 2.3 范围
- 规束后端路由组建包体落位原则、I18N 中英文多语言补全原则、ES Index 服务端自动注册装载流程，以及对四大基础社交响应共建模块（点赞、踩、活动流、版本史）继承和彻底执行强一致的“完全物理灭却”删除底线。

## 3. 需求内容

### 3.1 功能需求

#### 3.1.1 功能列表

| 功能点编号 | 功能名称 | 优先级(MoSCoW) | 简要说明 |
| :--- | :--- | :--- | :--- |
| F-001 | 新包专区与全向收束 | Must Have | 提供独立的包与文件簇约束。 |
| F-002 | ES全局倒排检索接入与打通 | Must Have | 新实体能被核心搜索网覆盖。 |
| F-003 | 双语字典强平替 | Must Have | 不保留任何硬编码和流出的键位占位字串。 |
| F-004 | OM核心社交套件加载继承 | Must Have | 五体并立皆有赞踩和动态及履历回溯能力。 |
| F-005 | 抹杀逻辑保留策略 | Must Have | 永久性移除原先在 OM 中常见的防沉迷“软删除”模式，采取直接抹消物理删除行为。 |

#### 3.1.2 功能详情 (基于 User Story)

**[F-001] 工程约束**
- 无论是前端的 Layout、Pages、Components 还是后端 Java REST 控制器或持久层实现，皆必须限定存放于带有 `asset` 等独立命名空间的专项隔离目录内。

**[F-002] 实体级搜索建导与对接**
- 系统 Boot 启动时，强制对全新的 `AssetCategory`, `AssetCatalog`, `AssetType`, `AssetAttribute`, `DataAsset` 实体簇进行 Mapping 推送建设出专设对应的 ElasticSearch DB 索引，并贯通全局主检索栏的响应通道。

**[F-003] 中英文对照词典**
- 一切视觉呈现层的外露提示符、Label与描述硬文必须全数纳入翻译库。限定必须交付英语 (en-US) 和简体中文 (zh-CN) 两大阵营的完满互释对照表，并作好 Fallback 英语的配置安全降级应对。

**[F-004 & F-005] 互动能力注入与销毁决绝准则**
- 使用底层继承，令这全部五名成员均天生具备：**Up Vote（赞） / Down Vote（踩） / Version History（履历带）/ Activity Thread（任务及事件交流留存台）** 四大配套附属服务系统，能够被前台正常调度响应调色反馈。
- **不可违逆指令要求**：完全根除上述这五大主实体的“逻辑隐蔽删除”接口概念方案集。数据库删除行为定义为永久清除底层表的对应 Row 物理数据。系统也不得对外开放召回、恢复这些删后数据的选项栏位接口。

### 3.2 非功能需求

- **稳定性**：要求与活动信息流对接时不能阻滞由于强事务锁或者大量轮询导致的服务降速。

## 4. 验收标准

### 4.1 验收标准 (Acceptance Criteria)
> 🚨【重要红线】这里是 QA 进行“测试左移”出题和“开发者自测”的唯一来源！每一条必须是非主观的、可被机器或人明确验证的条件。

- [ ] AC-01: **(环境孤立性检查测探)** Review 发现前后端的系统源码路径是否全数拘束和统合集中在于包含 `asset` 分类体系路径库包之内，未出现结构越权及飞蚊式随地乱抛代码散件情况。
- [ ] AC-02: **(语系倒转无缝呈现验证)** 在统一切换中文与英文状态后，全板块所有涉及文字标签的地方应对应呈现正确的对照内容字句组合形态，找不到一处保留有纯生键位特征（例如 `dataAsset.label.xxx`）等前端破损占位符。
- [ ] AC-03: **(统一全局热搜验证)** 搜索框顶部中输入某新建的上述五类实体相关任意一项独属特例名称后，具备回显及跨界穿透检索高光能力。
- [ ] AC-04: **(互动全覆盖确认)** 随意挑选和打开某项新增实体详情，皆能完成 Up Vote 的计数器增长且能在下部的 Activity Feed（活动流）栏中捕获并记录该动态发布足迹点印。
- [ ] AC-05: **(物理级无残留删切定检)** 在任何上述受体模块触发输入 DELETE 后进入执行的流程。于数据库管理台中复查该行相关 UUID 表实体。其必定全字段彻底抽没消失（而非标记 deleted 为 1 或 true 型隐藏作伪保留法）。

### 4.2 验收测试方案

| 测试场景 | 前置条件 | 操作步骤 | 预期结果 |
| :--- | :--- | :--- | :--- |
| 逻辑软删排查 | 落库多条资产测试对象备用 | 1. 通过 UI 执行标准删除并完成 DELETE 确认打回发送 ；2. 进入对应后台表单扫描执行 `SELECT * from entity_table where id = objectID` | 结果必须必定返回 Empty 空行集，代表已从存储主底座中物理擦除剔透不存在。 |

| 风险项 | 发生概率(高/中/低) | 影响面(大/中/小) | 应对机制（预防与缓解方案） |
| :--- | :--- | :--- | :--- |
| 强制物理删除由于存在大量附属历史（活动流/版本流等关联数据）造成阻断抛常态 Foreign Key Error | 高 | 大 | 删除实现层需要在底层 ORM 约束或手写 DAO 做一次级联周边所有该体所属信息表行连根抹净清除的事务闭式联动包裹。 |
